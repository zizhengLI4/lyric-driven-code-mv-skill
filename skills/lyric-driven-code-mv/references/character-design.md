# 主角外观卡与衣装连续性

这份说明规定角色设计的顺序：**先把主角设计成可画、可识别、能承载故事的人，再构思阻碍、配角、世界规则和分镜。** 主角不是故事写完之后随手补的一张立绘。

## 设计输入与优先级

按下面顺序取信息：

1. 用户明确给出的身份、外观、年龄范围、服装、色彩、参考图和不可修改项；这些必须保留。
2. 歌曲考据得到的时代、地点、创作问题和外部世界；这些用来解释主角为何这样穿、携带什么、行动如何可见，不把歌手本人直接当角色。
3. 歌词/音乐的核心意象和情绪变化；用来选择轮廓、材质、颜色和会随故事变化的状态。
4. 为像素画面服务的可读性；不能在目标尺寸下读出的细节不进入主角的必需设定。

只给歌曲时，先锁定歌曲背景和故事核心，再先生成主角外观卡；不要先列一堆配角或先选漂亮场景。用户只给了人物但没有衣装时，只补衣装和可视识别点，不改人物身份、关系或已有外观。

## 主角外观卡（最小完整字段）

每个主角至少记录以下内容，放进项目 brief、角色资产说明或同等可追踪的创作文件：

```text
角色 ID：p1
故事功能：主体 / 见证者 / 叙事视角
欲望与代价：他/她想得到什么，愿意失去什么
轮廓与体态：远景一眼可认的身高比例、肩线、发量或姿态
头发与脸部识别点：发型、刘海/发束、眼镜/面部标记；只留能画出的特征
主色 / 辅色 / 材质色：三组以内，说明颜色与人物处境或故事意象的关系
上装：具体款式、长度、层次、领口/袖口和主色
下装：裤/裙/短裤的轮廓、长度和颜色
鞋：形状与颜色；行走、奔跑或停留时要能读出
识别物：一个可反复出现的配饰或随身物，写明它与目标/代价的关系
目标像素简化：在当前虚拟网格/输出尺寸下保留哪三到五个识别信号
可变化状态：何时湿、破、沾光、失去配饰或换装；每次变化的故事原因
```

### 具体但不过载

- 外观要具体到能交给画法实现：不要只写“蓝色衣服”，要写“短款靛蓝雨衣、亮橙内层、左肩反光条”。
- 远景先保证轮廓、主辅色和识别物；近景再补材质、脸部和手上物件。
- 衣装不是装饰清单：袖口、反光条、湿痕、扣子、破口或配饰应该能参与动作、环境或情绪反馈。
- 主色变化要有原因，例如信号从冷青变暖橙、外套被雨压暗、识别物从持有变为留在对岸；不要为了换画面随意换色。

## 从主角再构思其他角色和故事

主角外观卡完成后，再从主角的欲望与外观构思阻碍、见证者/同伴和世界规则：

- 阻碍要能从主角的衣装、道具或身体动作上留下可见反馈。
- 配角的轮廓、配色或视线方向要与主角形成对照，避免两个角色在远景中混成一个人。
- 世界规则要解释主角为什么不能直接达成目标，以及哪些衣装/道具变化能表示代价、等待和回应。
- 每个角色新增的外观都要服务于关系或行动；不为了“画面丰富”堆无关服饰。

故事与分镜先围绕主角的“目标 → 行动 → 反馈 → 结果”展开，再把配角安排到会改变主角选择的位置。无歌词副歌或间奏也沿这条主角线继续推进，可以通过衣装状态、识别物位置、姿态、光线或环境反馈发展画面。

## 衣装状态与分镜引用

写基础衣装和可授权的变化列表，例如 `rain-coat`、`rain-coat-wet`、`no-lamp`；变化必须有时间或故事原因。跨镜核对：

- 主角 ID 不变；
- 默认衣装、颜色和识别物不自行跳变；
- `actors[].costumes[]` 是允许使用的名称；
- `scene.actors[].costume` 只引用该角色已有的名称；
- 用户给出的外观不被研究结果或后续配角设计覆盖。

当前 schema 不要求把完整外观字段塞进 JSON；JSON 负责稳定 ID 和 costume 引用，外观卡负责可读的设计依据。校验器通过不代表人物已经设计充分，仍需在目标像素尺寸抽帧检查剪影和识别点。

## 反面清单

- 先写“忧郁少年”，最后随便套一件外套。
- 主角、配角都用相同发色和相同轮廓，远景无法区分。
- 服装写得很华丽，但缩到实际像素尺寸只剩一团颜色。
- 每个镜头换一套衣服，却没有时间、环境或故事原因。
- 把歌手本人衣着或经历直接复制成角色，没有用户授权或来源依据。
- 只交付角色文字，不做目标尺寸下的剪影/识别点检查。

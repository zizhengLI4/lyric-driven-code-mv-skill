# 从一首歌到连续分镜

[作品与人物](#一先判定入口别问第二遍) · [可选热评](#听众热评怎么入镜) · [参考片取证](#参考片取证) · [代码绘制与提示词](#代码绘制与提示词)

适用：用户只丢来一个歌名/音频，没给人物也没给故事；或只给了人物、只给了剧情。
这一步的产物是**可校验的考据记录 + 人物卡 + 故事弧 + 连续分镜表**，不是"感觉一下这首歌讲什么"。

## 一、先判定入口，别问第二遍

| 用户给了什么 | 保留 | 要补 | 不许做 |
|---|---|---|---|
| 只有歌曲（或歌名） | 歌曲、版本、时长 | 创作背景考据 → 人物 → 故事 → 分镜 | 不要反问"你想要什么故事"；不要把歌词逐句直译成画面 |
| 歌曲 + 人物 | 人物 ID/外观/装束/关系 | 故事与分镜；考据只补人物所处世界的细节 | 不要换掉人物的外观或关系 |
| 歌曲 + 剧情 | 事件、结局、关键动作 | 人物功能位与外观；考据只补动机的合理性 | 不要改结局，也不要删用户给的关键动作 |
| 歌曲 + 人物 + 剧情 | 全部 | 只补分镜与实现 | 不要"优化"用户已确认的设定 |
| 没有歌，只有人物/剧情 | — | 先要音频或明确做无歌词版；无歌词版按分镜时间轴写旁白/字幕 | 不要凭空假定一首歌的时长与段落 |

缺什么补什么，已有的一个字都不动。补完直接进 分阶段制作 的 B 阶段，不重走 A 阶段。

## 二、联网考据：查什么，记什么

在允许联网时核查作品身份、创作背景和歌词提到的事实。同一关键说法优先交叉印证。接受史按需查，适用范围由实际读取的来源决定。

| 组 | 查什么 | 典型来源 | 用来干什么 |
|---|---|---|---|
| 作品身份 | 歌名、歌手、发行年、专辑/单曲、词曲作者、是否翻唱/采样/致敬 | 音乐平台曲目页、唱片公司页、维基/百科、版权登记信息 | 决定标题牌、年代感、片尾署名 |
| 创作意图 | 歌手/作者访谈、创作手记、专辑文案、直播或播客里的自述 | 官方访谈、杂志专访、官方社媒 | 决定故事的**真问题**（写给谁、为什么写） |
| 外部世界 | 歌词里的人名、地名、方言、行业、时代事件、器物 | 地方志/地图/博物馆/新闻档案 | 决定场景、道具、HUD 的单位 |
| 接受史 | 乐评、高赞评论、官方 MV 的视觉母题 | 乐评站、官方 MV、平台热评 | 决定母题与"观众已经在期待什么" |

记录格式（写进工程 `research.md`，同时落进分镜 JSON 的 `research` 块）：

```json
{
  "status": "verified",
  "song": { "title": "歌名", "artist": "歌手", "released": "2021", "writers": ["词作者", "曲作者"] },
  "sources": [
    { "url": "https://example.com/interview", "title": "歌手访谈：这首歌写给谁", "retrieved": "2026-11-18",
      "claims": ["写给他去世的祖母", "副歌的人声采样来自 1998 年的磁带"] }
  ],
  "facts": [
    { "claim": "写给他去世的祖母", "sourceIndex": 0, "confidence": "fact" },
    { "claim": "磁带是童年夏天的录音", "sourceIndex": 0, "confidence": "inference" },
    { "claim": "年代定在 1998 年的南方小城", "confidence": "creative" }
  ],
  "gaps": ["没有查到官方 MV，视觉母题按歌词内部证据设计"]
}
```

- `confidence` 只有三档：`fact`（来源直说）/ `inference`（你从来源推的）/ `creative`（你的设计）。**三档必须分开写**，否则后面会把设定当成史实讲给用户。
- `status`：`verified`（≥2 条来源且关键 claim 有印证）/ `partial`（只有作品身份）/ `unverified`（没联网或查不到，全部按歌词内部证据做）。
- 查不到就写进 `gaps`，并在交付说明中写明。离线或缺少可靠背景时，用歌词与器乐情绪推导情节，交付注明「原创演绎，非真实经历」。

### 听众热评怎么入镜

热评是可选证据。有助于理解歌词时，可查看同一录音版本的公开热评。记录平台、链接或评论 ID、查阅日期及实际读到的范围。评论区未开放、仅显示最新评论、或没有相关内容时，如实写入研究缺口，继续用歌词和已有背景设计。未实际读取评论正文时，禁止声称看过、引用或转述评论。

读热评时留意听众对哪句歌词有反应、想起了哪种日常经验，以及是否有人听出了另一种意思。筛掉互动玩笑和无关留言。用自己的话记下有画面价值的观察，保留个别观点的范围；点赞数仅用于说明排序。有关作者私生活或写作缘起的说法回到访谈、创作手记查证。

在制作笔记和分镜 research 中把采用项串起来：评论定位 → 听众理解 → 对应歌词或留白 → scene.id 与观众实际能看到的动作。可取一个手势、停顿、道具用法或回访方式。评论和歌词有张力时可保留张力；没有合适项就说明理由。用虚构角色重写可见细节，保护评论者身份，避免把个人故事直接搬上字幕。

### 三条硬规则

1. **歌手的人生不等于角色的人生。** 考据只用来定"真问题"和世界的质感；角色另起 ID、另设外观。直接把歌手本人当主角，会把 MV 变成纪录片。
2. **官方 MV 是参考片，不是分镜模板。** 要拆就按 拆一支参考片 采样 ≥12 帧、分事实/测量/推断三级；不能把它的镜头顺序当自己的分镜。
3. **歌词是证据，不是剧本。** 一句"我等了很久"可以写成倒计时归零、存档读档失败、车站时钟跳变；不要画一个人站着望天。

## 三、从考据到人物：只设四个功能位

任何故事都只需要四个位置。用户给了人物就把他/她放进对应位置，缺的位置补人，不要新增第五个主角。

| 功能位 | 必须回答 | 在 MV 里的可见形式 |
|---|---|---|
| 想要的人（主体） | 想要什么、愿意付出什么 | 主动作：完成任务、修复物件、发出消息、写入存档 |
| 挡住的人/物（阻碍） | 用什么挡、挡得多具体 | 锁住的门、断开的连接、时间限制、缺少资源 |
| 见证的人（对手/同伴） | 看见什么、误以为什么 | 同伴的表情、系统提示、告示牌、聊天框里的"对方正在输入" |
| 世界规则（装置） | 能不能见面、有没有时间戳、谁在看 | 从 叙事装置 选 1–3 个，写下"规则" |

人物卡（写进 `BRIEF.md`，字段与分镜 `actors[]` 对齐）：

```text
p1 主体 · 外观：短发 / 宽肩外套 / 站高 18px（虚拟网格）/ 朝右 / 持物点右手
    欲望：完成当前目标      代价：剩余时间或资源减少
p2 同伴 · 外观：长发 / 短斗篷 / 朝左 / 无持物
    欲望：帮助主体推进任务  误认：把系统提示理解成最终结果
rule 装置：按统一规则更新任务状态；已持有的道具跨镜保留
```

小精灵在 18–24px 时优先控制三类显眼信号：头部/发型形状、衣身/体态形状、稳定识别物；颜色只作辅助。去色并移除小道具后，至少仍有两类形状特征能区分角色。近景卡可细化脸部、材质和叙事细节，不把小精灵的信息预算套到近景。完整门槛见 角色差异度与完成度。

## 四、从人物到故事弧：三幕压到歌词句组上

把歌词按"谁在说话、想要什么变了没"切成 3–5 个句组，一个句组就是一幕。不要按每句一幕切，那是字幕 PPT。

```text
幕1（句组 A，约 0–35%）：立起欲望与阻碍。第一次行动，第一次失败。
幕2（句组 B，约 35–70%）：代价显现。重复副歌在这里必须给出新信息（新证据/新后果），不是复读。
幕3（句组 C，约 70–100%）：结局。成功、失败或尚未完成但留下了可见后果；留白句交给画面，不加旁白。
```

每幕写一行因果，格式固定：**目标 → 行动 → 反馈 → 结果**。四段缺一段就是空镜。

- 反馈必须落在画面上：数值变了、路线断了、灯亮了、档坏了。
- 结果必须改变下一幕的起点，否则删掉这一幕。
- 结局可以在歌词里没写；允许"未完成"，但要有可见的代价留下。

## 五、从故事弧到连续分镜

"连续"指同一件东西跨镜不消失、同一处伤不自己好、同一套规则不破例。落地成 `scenes[]`：

1. **镜头 ID 用语义命名**（`send-and-stop`、`other-bank-sees-light`），不用 `shot1`；改动时靠 ID 定位影响范围。
2. **镜间不重叠不留洞**（`end` 必须等于下一镜 `start`）；切点只允许在句边界或重音上，不在字中间。
3. **每镜必须有事件**：至少一个 `events[]` 或一次道具变化，否则抽帧看不到变化（校验器会给警告）。
4. **跨镜连续性三件套**：道具持有者、人物位置、HUD 当前值。写进 `outcome` 和下一镜的 `objective`，让它在文字上就连续。
5. **重复段落加信息**：第二次副歌可以换视角、展示新证据或增加代价；若结局发生变化，应由歌词与人物行动支持。
6. **每 8–12 秒一次可读变化**（HUD/字幕/动作峰值/材质），用 `hud-density.mjs` 量，不靠感觉。
7. **出口转场写清楚**：`exitTransition` 记录镜头如何离开以及哪些状态要延续。例如横向移动时保留人物位置和当前道具状态，让下一镜接得上。

分镜写完先跑：

```sh
node scripts/validate-storyboard.mjs --strict path/to/storyboard.json
node scripts/hud-density.mjs path/to/storyboard.json --max-gap 8 --strict
```

两条都过，才进 B 阶段静帧。校验器不证明歌词语义正确，只证明结构与记录完整。

## 六、反面清单

- 把歌词逐句配一张图：15 句 15 个场景，观众只看到字幕换背景。
- 用考据到的歌手生平直接当剧情：主角变成"歌手的替身"，人物卡失效。
- 人物只写"忧郁少年"：18px 里读不出来，画出来每帧都一样。
- 结局靠旁白说：字幕写"他终于放下了"，画面什么都没变。
- 母题首尾失去联系：开场反复出现的物件，在结尾突然被无关元素替换，观众难以读出呼应。
- HUD 没有单位：`数值 87`、`进度 100%`，读者不知道 100% 是什么满了。

## 主题与可读性

1. **归纳原作。** 在歌曲地图上挑出开头的处境、转折处改变的事实、结尾仍未解决或已经改变的事。每条记一个词句或可定位的音乐变化。重复句合并记录，同时注明第二次出现前听众多知道了什么。把叙述者、被唱到的人、时间顺序和明显歧义区分开。
2. **选择解释。** 写一句对作品的具体理解。若只能写出“爱、遗憾、成长”，追问“谁想要什么，两件事为什么不能同时得到，最后怎样面对”。有两种可信解释时，用最难解释的那一句歌词检验各自的解释。歌里没有给出的离别原因、职业和结局都标为原创改编。器乐或开放式作品可保留多义，写清观众应察觉的情绪变化。
3. **翻译为画面。** 在草图中并排放开头、转折和结尾，给每张各写一句只描述可见动作的话。开头交代关系与眼下的问题，转折让一个决定产生后果，结尾回到开头的具体事物并改变它的用途。例如，开头摆两套餐具，离别后每天照摆，结尾终于为自己热了一顿饭。示例中的道具按歌曲另选。
4. **检查场景是否够用。** 逐段问“观众在这里新知道了什么”。同样的地点能承载不同决定；只有取景或字幕在变时，合并空转镜头，或补上缺失的行动、对方的反应、具体后果。副歌重现时核对它是否推进了先前的选择。
5. **交付前复评。** 先暂时隐藏歌词和剧情说明，看首段能否认出关系、在关键动作之后能否辨认改变、从尾镜能否推回立意。再恢复歌词，检查歌词和画面是否相互支持，以及演唱字幕和原创对白能否区分。若没有独立观众参与，记录为作者自检。若难以读懂，先返修提供线索的镜头。

## 参考片取证

参考片分析先记录来源、取证日期、访问方式、样本范围、采样方法和文件哈希。页面能显示的内容与视频本身能证明的内容分开保存，不能用平台页面的自动整理替代作者原话、完整画面或音轨证据。

### 证据分层

按证据来源给每条观察标记，至少区分以下几类：

1. **页面元数据**：标题、作者、发布时间、时长、平台声明和原始链接。它能证明页面展示了什么，不能证明作者完整制作过程。
2. **平台自动章节摘要**：平台生成的章节标题、时间点和摘要只作为导航线索。除非在视频画面或音轨中复核，否则不要写成“作者在某秒说了”或“作者实际执行了某步骤”。
3. **可见画面证据**：播放器中实际看到的构图、字幕、角色、HUD、材质变奏、章节牌和镜头区间。抽帧或截图要记录时间点与分辨率。
4. **音频证据**：实际听到的歌词、重音、停顿、BPM 候选和音画落点。浏览器标注静音、无法播放或没有人工试听时，写明“未试听”，不宣称逐词或卡点已验证。
5. **作者材料**：作者原话、提示词、工程、源码或明确的制作说明。没有这些材料时，模型名称、提示词、渲染框架和后期链路保持未知。

把结论分成三层：

- **可见事实**：直接来自页面或画面，并注明来源层级。
- **可复现测量**：视频时长、分辨率、抽帧时间和出现次数，并保留命令或采样表。
- **推断与建议**：可能的实现框架、缓动曲线、粒子生命周期和音画同步，明确写成推断或本项目建议。

均匀抽帧适合建立横向样本台账；它不能证明逐帧动效或真实节拍。页面章节摘要不能证明作者实际步骤，静音播放不能证明歌词或重音落点。若要升级结论，补做音频分析、逐帧抽查或取得作者工程说明，并在记录中标注新增证据。

建议台账字段：`作品 id`、`原始链接`、`取证时间`、`访问方式`、`页面元数据`、`chapterSource`、`时长`、`分辨率`、`采样点`、`device`、`chapters`、`hud`、`materialVariant`、`audioStatus`、`作者材料`、`事实`、`推断`、`未知项`、`限制`。

#### 可迁移的制作要点

- A/B 共同支持一条可分阶段检查的路线：拆解实际歌曲与歌词 → 确立人物/故事及视觉方向 → 先核静帧 → 需要时制作短动态样片 → 按已确认方案扩成片。样片服务于动作、衔接、字幕等动态风险检查，用户可以跳过。
- C 的成片方向不是只复用标题卡，而是把标题与菜单做成进入游戏世界的序章，再用地图、角色行动、对话框和状态 HUD 贯穿段落。可借用界面职责与状态变化的组织方式，具体角色、文字、地点和素材仍为新项目原创设计。
- 屏幕计数、关系心形或竖向状态条，应在对应的人物行动或场景事件后更新，并把改变后的状态带入后续镜头。这个因果映射属于从画面得到的制作建议，不代表我们获知了作者的内部工程规则。
- ASR 支持定位三条视频讲解主题的大致区间；歌词识别不够可靠。精确歌词、音乐重音与视听同步需要人工听辨或其他直接证据。

## 代码绘制与提示词

本页把 Win-Hao 公开的代码视频与 MV 提示词工作流，改写成可在歌词驱动代码 MV Skill 中复用的方法。项目作者说明 `code-video` 用 Opus 5.5 + Claude Code 做过实践测试；其 `music-mv` 教程展示了：先理解歌曲、再定画风与角色、逐句写分镜、先看关键帧总览、最后代码逐帧渲染并复查。可迁移的关键不是“换成更强模型”，而是让编程模型按明确阶段写代码、产出可预览证据，并依据真实帧逐轮修改。

**边界：**这不是 Opus 5.5 的内部工作原理，也不证明任何特定 MV 引擎存在。以下提炼依据公开提示词与 README；不把外部教程中的具体文件名、单网页实现或私有提示卡说成所有工程的必需做法。用户指定用代码画时，直接用当前工程的 Canvas/SVG/Pillow/浏览器帧接口；不换成图像生成服务，也不需要 API Key。

#### 提示词结构：先分阶段，再精确指定

公开 `code-video` README 正文列出六个核心 XML 块，仓库 About 将单独列出的 `avoid` 计入后称“七块”。实际要点是这些命名标签可分离意图；按需填写，不要把整支 MV 一次性交给单条大提示：

- `<role>`：给当前阶段一个具体职责和质量优先级（如“像素美术指导，首要保证动作一眼可读”）。
- `<context>`：作品用途、观众、已确认的人物/画风/镜头、现有工程和时序。
- `<task>`：这一阶段要做什么、展示什么、观众应记住什么；控制在可独立验收的范围。
- `<specs>`：尺寸、帧率（写“每秒帧数”）、时长、绘制入口、图层/锚点、音频与文件路径等可执行约束。
- `<style>`：推荐画法及理由，具体说明调色板、像素尺度、光线和材质；点名要避免的陈词滥调，不写空泛的“高级感”。
- `<check>`：检查哪些样帧、动作点或转场，以及通过条件。

`music-mv` 的部分提示另有 `<avoid>` 块。本 Skill 也把禁项单独列出，让重复出现的问题易于定位；这只是本 Skill 的适配格式，不是 Claude/Opus 的固定语法。禁项要具体（如“没有语义的漂浮徽章、紫色霓虹、整屏渐变”），避免只写“不要 AI 味”。模型或 agent 的自检说法不是证据；保留实际命令、关键帧和未通过项。

### 代码控制的分阶段工作流

#### 1. 先理解歌曲与歌词时间

先校对歌词，记录歌词行起止、段落、停顿与节拍候选。不确定的转写或拍点标成待确认。分别记录音乐时间线和语义/事件线；未听清的一句不让模型靠猜来编道具。此阶段交歌词校对与时间分析，不画完整 MV。

#### 2. 用代码定画风，不急着做成片

用歌词中的同一主角、构图和动作画三张候选：一个稳妥、一个大胆、一个最贴合歌词意象；每张只改变画法，不偷换主题。每种风格都要用它原生的代码绘制方法，不可拿同一张图套像素化/纸纹滤镜伪装画风。每张样图附画法和适配理由，拼成可比较的预览交用户选择；获选后把最终提示词/画风规格保存为 `prompt.md` 或工程现有的设计文件，后续镜头沿用，不反复发散。用户已确认某一风格时，跳过多风格再提案。

像素样帧明确虚拟分辨率、色板上限、像素簇、整数倍放大与最近邻关闭平滑。指定真实禁项，比“有电影感”“不要 AI 味”更可执行。

#### 3. 把角色和物件做成可复用接口

身份/形状放在共享角色或物件绘制模块中；镜头只传姿势、朝向、表情、开合状态、位置与持物锚点，不能每个镜头都重新捏一张“相似角色”。先检查角色图、纯黑剪影和动作关键姿态，再复用到分镜。物件要有轮廓、材质、前后遮挡和接触面；同一物件跨镜头保持外形与关键特征一致。

#### 4. 每句先写视觉账本，再写绘图代码

按[视觉账本示例](../assets/examples/visual-ledger-demo.json)组织镜头、可见物件、动作与结果。

每一条 cue 至少写清：

`歌词ID/时间 → 观众应读到的意思 → 主体和具体物件 → 两条识别特征 → 景别/构图 → 准备 → 接触/动作 → 可见结果 → 材质/光线/细节 → 出镜状态`

让模型先回答：这个东西实际是什么？这句里为什么出现？不看字幕能凭什么认出来？它被谁碰到、碰到哪里、动作后变成什么状态？答不清就简化或换成歌词本身更具体的物件；不要用设计者自己也解释不了的符号填空。

“场景”不等于“镜头”。同一地点可容纳数句，但每句要给出新的视觉信息——换焦点、推进动作、改变景别/视角，或展示动作结果。约四五句后检查是否应换场或出现新事件；这是审查阈值，不是每句机械硬切。短句可合并成一个完整动作，长句可拆为准备/接触/结果。单纯字幕变化、微小平移或同一张大背景不能冒充逐句演出。

#### 5. 先画关键帧总览，让问题早暴露

分镜完成后先为每镜的关键状态出静帧，拼接触表；需要时包括每句的开场、动作峰值、接触和收束帧。先检查主体是否易认、含义是否读得懂、跨镜身份与道具状态是否连续、构图和细节是否被字幕遮住。静帧通过后才实现动画；关键帧不能证明动画已经完成。用户已认可的转场若不在本轮问题范围内，明确冻结，不趁机重做。

#### 6. 统一时间，让代码能任意取帧

沿用现有工程契约，不为模仿教程而强制迁移到单网页。用 `renderAt(t)` 或项目等价函数，让背景、角色、物件、歌词与转场都从同一成片时刻 `t` 求值。禁止依赖上次绘制累积的位置、浏览器实时帧率或未固定随机数；相同 `t` 和输入必须产生同一帧，才能跳播、离线渲染、倒序检查和精确改镜。关键动作标注准备、接触/峰值与结果的帧/秒区间。歌词/时间数据保留一份真源，代码按稳定 ID 取用，避免重复维护文案和时间。

像素绘图使用整数坐标和整数倍最近邻放大，关闭平滑；检查像素颜色数和边缘时看无损 PNG 帧，而不是有损 MP4。粒子需要随机性时固定种子。

### 工具链：代码、浏览器、编码器各司其职

作者公开的 `music-mv` 示例将绘画与编码分开：

- **画面代码**：HTML Canvas 2D 是常见起点；p5.js/p5.brush 用于需要笔触的绘本，Three.js 用于确有需要的风格化 3D。角色、物件、镜头仍由代码控制。
- **逐帧渲染**：Node.js 18+ 执行 `render_frames.mjs`，用 Puppeteer 驱动本机 Chrome/Edge/Chromium，按帧率调用页面的 `renderAt(t)` 并保存图片。`puppeteer-core` 使用已有浏览器；`puppeteer` 可携带浏览器。
- **画面与音频后期**：FFmpeg/FFprobe 负责编码、接回原曲和核验；浏览器负责运行绘画代码并截图，不负责决定歌词/镜头意义。
- **Python 工具**：来源仓库列有 Python 3.9+、`numpy`、`librosa`、`Pillow`；其中 `librosa/numpy` 用于歌曲结构与拍点分析，Pillow 用于部分图像工具。Whisper 是可选歌词转录依赖，用户已有校对歌词时不必安装。
- **替代渲染器**：同作者 `code-video` 公开的是 Playwright + FFmpeg；与上述 Puppeteer 路线二选一，不必同时安装。

复现外部教程时，依赖预检可参考来源仓库 `scripts/check_env.py` 和 `requirements.txt`，不只看“浏览器能打开”。项目若需要安装 Node 包、浏览器、Python 包，先说明具体依赖和用途并征得同意；`puppeteer` 可能下载浏览器。不要只为复现教程而添加付费服务或重型框架。

本 Skill 的实际依赖以「依赖与交付」和本地预检结果为准。HyperFrames/Remotion 和现有工程仍优先，不为复现教程迁移框架；只吸收代码接口、逐帧证据与检查方式。代码与依赖准备好后，渲染不要求 Opus 5.5 在线参与；模型写程序，渲染器按时间确定性运行。

### “丝滑”从哪里来

1. **同一时钟**：角色、道具和相机都按同一个绝对成片时间求值；相邻镜头短暂重叠，转场期两个镜头共同参与合成，避免独立图层推拉错位，或靠硬切遮住状态断裂。
2. **缓动而非匀速**：相机推进/甩镜用平滑的 `inOut`；物件落下/滑入可用 `out`；需要弹性时只在落位阶段用克制的 `back/spring`。若曲线过早到位，把曲线区间延到重拍附近，或换一条合适的曲线；不要为了“顺”错过音乐落点。
3. **准备在拍前，结果落在拍上**：动作可在重拍前约 0.2–0.5 秒起步，精确接触/构图峰值落在核对过的节拍。每个镜头只保留一种缓慢运镜；甩镜、旋转等大动作主要放在转场，避免镜头内反复推拉和每拍抖动。
4. **转场保证空间连续**：预先选一种全片主方案；每个切点说明动作接动作、匹配形状、遮挡、推进或有意硬切。用遮挡覆盖切点；接续镜头的方向、速度、人物尺度和道具状态要吻合。
5. **动态模糊只给快速运动**：参考实现以 `blur(t)` 对一帧做多时刻子帧采样并合成，而不是整帧糊化；歌词/HUD 放在清晰的独立覆盖层。子帧数随运动量调，太少会有分离残影，太多则拖慢渲染。
6. **集中检查切点**：先渲最难一段；每个转场点前后约 0.6 秒按约 0.1 秒抽帧成排查看，并单独检查切点头两帧和动作接触帧。通过条件：位置/速度连续、无黑帧/空帧、动作峰值落在所选音乐点；之后再扩展整支。

这些是可复现的制作方法，不保证作品自动达到参考片质感；曲线、模糊和过冲量仍需根据歌曲、画风和输出尺寸复核。

#### 7. 选择动态验证时用短样片逐轮修正

先完成用户指定的范围，不默认扩成整首。动态动作或转场需要验证时，渲染静帧、接触表和短动态样片；否则用静帧及时间数据完成静态检查，并把无法从静帧判断的动态项列为待验证。关闭字幕的画面检查歌词有没有被具体演出呈现。检查手机实际尺寸、动作峰值、每个转场头尾；条件允许时再逐帧查看转场附近约 0.5 秒，排查空帧、出画、跳姿、穿插、手物脱离和局部飞散。每轮把一个可定位问题改到具体 cue/资产，按同样时点比较；需要动态验证时重渲受影响片段和邻镜，通过后再扩展。

### 画面精致度不是“增加元素”

先保证大形、明暗分组与焦点，再逐层细化：轮廓/负形 → 主色块 → 受光面与投影面 → 材质专属高光/纹理 → 少量身份细节 → 手持接触、遮挡和动作痕迹。金属用克制的断续高光；布褶服从受力方向；纸张呈现厚边/折痕；液体需有容器轮廓和液面。全片统一像素簇尺度、调色板和主光方向。只加目标尺寸可读、且说明材质/身份/动作的细节。

同时看两种尺度：无字幕最终尺寸检验物件和动作能否读懂；像素近景检验轮廓、材质和边缘。若缩小后物件变成无意义色块，先重做剪影和占屏比例，不要靠加纹理或提高成片分辨率弥补。

### 工程检查覆盖的范围

导出与检查脚本会拒绝输入输出路径别名，帧恢复会检查实际源码、分镜和音轨指纹。构图统计给出色频和主体估算比例，分镜校验读取实际拍点容差。SFX 报告记录混音瞬变、同期原曲差分和独立 SFX 电平。人工复听单独记录。结构通过后用实际静帧与逐镜审片验证画面中看得见的事件、接触和跨镜状态。
